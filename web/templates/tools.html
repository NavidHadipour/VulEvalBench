Model infrastructure

Three separate services provide the models this framework uses. Knowing which is which explains why the dropdowns on the run page list completely different names from one another.

ServiceRuns whereUsed for Chosen on the run page asCost
Ollama this machine, port 11434 generating benchmark samples Generator model free
Judgment API remote, OpenAI-compatible judging, LLM detection, embeddings Judge A / Judge B, LLM detector per token
Anthropic remote (optional) optional second-vendor detector — per token
  • Ollama is a model server, not a model. There is no “use Ollama” option to tick, because selecting any tag in the Generator dropdown already means Ollama — that list is populated solely from what your local Ollama server has pulled (ollama list). Add to it with ollama pull <name> and reload the page.
  • Generation runs locally on purpose. It is by far the most token-hungry stage — two complete programs per call — so running it locally makes scaling to several hundred samples free. It also guarantees the model that writes a sample is never the model that certifies it, which removes self-preference bias by construction.
  • Generator size is a hardware decision. Without a CUDA GPU, Ollama runs entirely on CPU. On the development machine qwen2.5-coder:3b took ~45 s per pair while qwen2.5-coder:7b took ~457 s and repeatedly ran out of memory. Check ollama ps while a model is loaded: a PROCESSOR column reading 100% CPU means no GPU offload, and larger models will be slow.

How the arms are measured differently

  • Static analysers report findings, not per-file verdicts. A file with no relevant finding is taken as a claim that the file is clean. By default only findings whose CWE is in the benchmark's catalogue count towards a verdict — otherwise unrelated hygiene warnings (“request without timeout”) would flag every sample and push the false positive rate to 1.0 for reasons unconnected to the question being asked. Both the scoped and unscoped finding counts are recorded in every result file.
  • ML models are the only arm that learns from the data it is scored on, so every prediction is made out of fold: the model that labelled a sample was fitted without ever seeing it. Scoring them on their training data would report memorisation as detection and would be wildly unfair to the other two arms, which never see a label at all. This difference in protocol must be stated in any write-up.
  • LLM detectors are shown the candidate CWE list so their category answers are comparable with ground truth. That is a small advantage over the static tools, which map findings to categories through a fixed rule table and cannot choose from a list.
  • The default LLM detector is deliberately a different model from the judges. A model that helped certify a sample must not also be graded on finding the vulnerability in it.

Adding another tool

A new detector joins the comparison by writing the common result shape into a run's 03_detection/ directory — nothing in evaluate.py changes. Register it in src/detectors/__init__.py and add its runner to RUNNERS in src/detect.py. 

{
  "detector":      "My tool",
  "detector_key":  "static_mytool",
  "detector_type": "static",
  "predictions": [
    {"id": "sample_001",
     "predicted_label": "vulnerable",
     "predicted_cwe":   "CWE-89",
     "confidence":      0.82,
     "reasoning":       "why"}
  ]
}

Semgrep was the original second static analyser and is what the earlier draft named. It is absent here because it has no working Windows distribution — pip install semgrep succeeds but installs no runnable binary. On Linux, or inside the Docker image, it drops in as a third static detector without changes outside src/detectors/static_tools.py.
